# 审核轮次与筛选核对

本规则用于消息读取后、正式待办写入前。读取范围、本人身份和原有完成记录不变。

## 按本轮职责判断

- “我看完了，你再看看问题”表示首轮已审并要求对方修改，不表示修改后的复核已经完成。
- 同一工作随后出现“设计稿更新了”“改好了”“请再看”等回稿，结合前文重新判断本人复核动作。对方负责制作，不排除本人审核职责。
- 同事转来变更内容，先判断本人需要审核范围、方案还是仅知会。只有证据支持时才列正式待办；归属或动作有歧义时保留待确认，不静默丢弃，也不自动把对方执行任务指派给本人。
- 明确尚在修改中，保留“待他人反馈”的触发条件，不声称已交付；本人已经明确完成当前轮次才关闭。上一轮的完成证据不能关闭后来的回稿。
- 已完成的旧key不自动重开；有明确新一轮审核则建立关联的新轮次。未完成事项继续更新同一key，不因重复消息重复建项。

## 可检查的筛选记录

collect用少量文本匹配提名审核、回稿、转发变更线索，并把原消息及同会话上下文保存在review-candidates.json。此步骤仅做补漏，不能覆盖所有自然语言，也不自动判断责任。AI仍须阅读全部证据，并补充未命中但真实存在的待办。

把ledger_template中的每条线索填写到独立review-ledger.json数组。每条候选必须有且仅有一个去向；证据ID只能引用该候选context里的真实消息：

```json
[
  {
    "candidate_id": "来自候选的消息ID",
    "decision": "task",
    "item_key": "已写入主表的当前未完成事项key",
    "reason": "本人已审首轮，对方后续回稿，仍需本人复核。",
    "evidence_ids": ["来自context的回稿消息ID"]
  }
]
```

去向及额外字段：

| decision | 要求 |
|---|---|
| task | item_key必须指向已入账的当前未完成事项，不能指向已完成的旧轮次。 |
| needs_confirmation | 填label（60字以内）和具体待确认原因；线索跨日保留，并在清单正文提示，不混进正式待办数量。 |
| exclude | 必须填reason_code、具体理由和真实证据。可用informational_only（纯知会）、unrelated_to_user（与本人无关）、not_actionable（并非行动请求）、user_completed_after（本人在此消息之后已明确完成本轮）、delegated_by_user（本人随后明确将审核职责转交他人）。 |

不能用“项目不明确”“别人负责执行”“上一轮已审”作为排除依据。回稿之前的本人审核不能证明当前回稿已审；user_completed_after需引用回稿之后的本人完成消息，并填completion_quote原文短句。校验会检查时间、发送人、原文及基本否定表达；最终是否属于同一项目和同一轮次仍由AI核对，不能把校验通过当成分析必然正确。

delegated_by_user需要随后本人明确转交审核职责的原消息及delegation_quote短句，不能仅因别人负责制作或修改就声称本人不再审核。进度线索与最终回稿分开，不把“请更新一下”“正在修改”直接判成交付完成。

运行upsert并同步主表后，使用daily.md中的finish-scan命令。校验失败时修复本地筛选记录，不能跳过校验推进水位。候选有歧义时可以needs_confirmation保留后正常通知；仅真正缺失核对记录时阻止发送并报告失败。运行记录仅在个人数据目录保存，不上传工具仓库。

在线guidance更新可让旧安装读取同一分析原则；新增的代码校验需要1.3.0及以上安装包。不要声称旧版已自动获得代码。
